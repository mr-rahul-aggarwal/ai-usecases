An automated claims-decisioning agent

An Agent That Reads the Policy — before it pays, denies, or escalates a claim

Auto insurance claims are still mostly adjudicated by hand: an executive reads an invoice, flips through a policy document, and decides. This case file first sets out, at a high level, what an agent would need to do to take on that job responsibly — and then walks through the shared repository where that agent is actually built: the workflow, its tools, its knowledge base, and how to run it.

The case for an agent in the claims file

Claims processing today runs on manual review of invoices against a policy document that is long, dense, and updated on its own schedule — exactly the conditions under which people make inconsistent calls.

The manual file, today

  • ReviewerA claims executive, by hand
  • ReferenceThe full policy document, read start to end
  • ChecksVendor terms, payment stipulations, subject-matter judgement
  • Failure modeClaims denied on invalid grounds, or inflated ones approved
  • CostSlow cycle times, rising overhead, client frustration

The agentic file

  • ReviewerAn LLM agent with retrieval and a set of specialised tools
  • ReferenceThe same policy, held in a form the agent can search
  • ChecksCoverage validity, relevant policy clauses, a price sanity check
  • Failure modeCaught early — an invalid claim is stopped before it goes further
  • OutcomeThe same claim, read the same way, every time
FIG. 2

Why agentic RAG, and not a plain retrieve-then-generate pipeline

A traditional RAG pipeline retrieves once and answers once. A claim isn't a single lookup — it needs validation, a priced sanity check, and a decision that can stop early. That calls for an agent that plans its own next step.

Traditional RAG

  • WorkflowStatic: retrieve, then generate, once
  • AdaptabilityLow — one pass, no branching on what it finds
  • Multi-step tasksNot a natural fit
  • Self-correctionNone built in

Agentic RAG

  • WorkflowDynamic: reflection, planning, tool use, collaboration
  • AdaptabilityRetrieval and context are refined as the agent reasons
  • Multi-step tasksSequential or collaborative operating structure
  • Self-correctionCan route around an invalid or inflated claim

What the agent is responsible for

Stripped of implementation detail, the job breaks into six responsibilities, each one gating the next so a bad claim is stopped as early as possible.

1

Understand the claim

Turn the raw submission into a structured record the rest of the workflow can act on.

2

Check it's valid

Confirm the claim actually qualifies before any policy lookup or pricing work is done.

3

Know where to look

Work out which parts of the policy are relevant to this specific claim.

4

Bring back the right text

Retrieve the matching policy sections from the knowledge base.

5

Weigh coverage and price

Decide what's covered, and sanity-check whether the amount asked for is reasonable.

6

Commit to a decision

Approve, deny, or flag for review — with a reason attached every time.

Six tools, one claim passed hand to hand

The repository implements the six responsibilities above as six callable tools. Each one takes the output of the last and hands back a little more structure.

TOOL 1

parse_claim

Prompts the model to read the incoming claim JSON and extract the claim ID, policy holder, vendor name, invoice items, and claim amount into a clean JSON object.

in: claim json   out: parsed fields
TOOL 2

is_valid_query

Prompts the model to confirm the claim has all required fields, a claim amount above zero, a named vendor, and an identified policy holder — returning a validity flag and a reason.

in: parsed fields   out: is_valid, reason
TOOL 3

generate_policy_queries

Prompts the model for 2–3 targeted search queries covering coverage for the service type, vendor requirements, and claim-amount limits.

in: parsed fields   out: list of queries
TOOL 4

retrieve_policy_text

Runs each generated query against the policy knowledge base and combines the top matching sections into a single block of retrieved text.

in: queries   out: policy text
TOOL 5

generate_recommendation

Weighs the claim against the retrieved policy text and returns an APPROVE / DENY recommendation with supporting reasoning.

in: claim + policy text   out: recommendation, reasoning
TOOL 6

finalize_decision

Combines the recommendation, its reasoning, and the price-check result into a final APPROVED / DENIED / REQUIRES_REVIEW decision.

in: recommendation + price check   out: final decision
FIG. 5

The workflow as a state machine

The six tools are wired into an eight-node LangGraph workflow. The single branch point — is the claim valid? — is the graph's one conditional edge; every other step runs in a fixed order.

Three ways to stand the service up

The Readme documents three install paths, from a from-scratch cloud build down to a local virtual environment.

PATH 1

AWS EC2, from source

  1. Launch an Ubuntu EC2 instance, install Docker
  2. Clone the repo and add API keys to .env
  3. Build and run the image
docker build -t insurance-agent:v1 . docker run -d -p 80:8501 insurance-agent:v1
PATH 2

Docker Hub, pre-built

  1. Install Docker on any instance
  2. Pull the published image
  3. Run it with keys passed as env vars
docker pull gr8learning/insurance-agent:v1 docker run -d -p 80:8501 \ -e OPENAI_API_KEY=... \ gr8learning/insurance-agent:v1
PATH 3

Local virtual environment

  1. Create and activate a venv
  2. pip install -r requirements.txt
  3. Add keys to .env, then launch
streamlit run app/main.py # http://localhost:8501
Takeaways

The repository turns claims processing into a workflow, a retrieval layer, and an interface — each one packaged so it can be run, tested, and shipped on its own.

01

An explicit state graph makes the decision auditable — eight named nodes you can log, test, and pin independently, with exactly one branch point.

02

Validation is a policy decision, not just a prompt. Whoever owns that one tool owns the reason a claim gets denied.

03

Shipping is part of the deliverable. The same graph ships three documented ways — EC2 build, Docker Hub pull, local venv.
